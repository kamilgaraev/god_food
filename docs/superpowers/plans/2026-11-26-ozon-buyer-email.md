# Исправление обязательного email в Ozon Доставке

Причина заказа №587 подтверждена сохранённой диагностикой `HTTP 400. 3; The "email" field must be filled in`. В WooCommerce сохранён корректный email, в нормализованном запросе buyer.email отсутствует. Ozon объявил поле обязательным 13 ноября 2026, https://t.me/OzonSellerAPI/726.

- [x] Покрыть регрессией реальную сборку buyer при отправке, включая старый сохранённый payload, изменённый email и отсутствие/некорректность email. Сохранить данные доставки и получателя.
- [x] Перед каждым первым созданием брать email из сохранённого заказа, проверять и включать buyer.email. Уже созданные отправления пропускать. Не отправлять значения email в журналы.
- [x] Прогнать существующие тесты интеграций и выполнить dev-проверку штатного обработчика с перехватом всех внешних запросов. Проверить сохранение order_number/posting_number и повторный вызов без дубля.
- [x] Проверить доступные идентификаторы №587 и описать восстановление. Реальное создание отправления требует отдельного разрешения после проверки запроса. До согласования выкладка только на dev, код в отдельной ветке Git.

Номер заказа Ozon и номера отправлений возвращаются успешным /v2/order/create. Текущий HTTP 400 не содержит этих номеров. Для восстановления перед повторным созданием проверяются кабинет/список FBS, отсутствие уже созданного отправления и актуальность сохранённого расчёта.

Проверки завершены. 163 unit-теста прошли, штатный обработчик на staging проверен в памяти с перехватом HTTP. Подтверждены buyer.email, сохранение order_number и posting_number, отсутствие повторного вызова для созданного отправления, понятная ошибка при пустом email и поддержка legacy ID. Read-only review не выявил важных ошибок.

Read-only поиск через /v4/posting/fbs/list вернул 14 отправлений за 26 ноября, совпадений по SKU и количествам №587 не найдено. Старый /v3/posting/fbs/list вернул 404. Поиск не создавал отправлений. В сохранённом расчёте №587 цена перевозчика 980 RUB и окно 5 декабря.
