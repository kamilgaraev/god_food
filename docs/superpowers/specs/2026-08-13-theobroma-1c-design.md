# Интеграция WooCommerce с 1С

## Цель

Создать принадлежащий проекту плагин `theobroma-1c`, который безопасно передаёт оплаченные заказы WooCommerce в 1С по CommerceML и может расширяться для статусов, возвратов, остатков и цен. Первая версия не разрешает 1С изменять каталог сайта.

## Границы первой версии

В первую версию входят:

- защищённая точка обмена с 1С;
- CommerceML-экспорт заказов;
- выгрузка только оплаченных заказов и последующих изменений уже выгруженных заказов;
- передача отмен и возвратов;
- независимые товарные идентификаторы;
- поля идентификаторов в редакторе товара;
- массовая загрузка TSV/CSV-выгрузки Ozon с предварительным просмотром;
- журнал и диагностика без секретов и персональных данных;
- автоматические тесты и WordPress smoke-проверка.

В первую версию не входят:

- импорт товаров, категорий, цен, остатков и изображений из 1С;
- создание или обновление товаров из 1С;
- изменение заказов WooCommerce по данным из 1С;
- фоновая отправка сайтом запросов в 1С;
- двусторонняя синхронизация каталога.

## Архитектура

Плагин располагается в `wp-content/plugins/theobroma-1c` и не зависит от стороннего EDI. Он следует структуре существующего `theobroma-commerce`: тонкая WordPress-регистрация, отдельные сервисы, DTO и чистые построители CommerceML.

Основные компоненты:

- `Plugin` — регистрирует endpoint, настройки, товарные поля и lifecycle заказов.
- `Settings` — хранит логин, хеш пароля и флаг включения обмена. Пароль никогда не возвращается в интерфейс и журнал.
- `ExchangeController` — принимает HTTP-запрос, проверяет Basic Auth, валидирует `type`/`mode`, вызывает сервис и формирует протокольный ответ.
- `OrderExportService` — выбирает заказы для выгрузки и подтверждает их выгрузку.
- `CommerceMlOrderWriter` — формирует CommerceML 2.05 из DTO заказа.
- `ProductIdentifierResolver` — выбирает основной идентификатор и формирует дополнительные реквизиты позиции.
- `OrderLifecycle` — отмечает заказ как требующий выгрузки после оплаты и после значимых изменений.
- `OzonCatalogImporter` — разбирает TSV/CSV, строит предварительный отчёт и применяет только подтверждённые однозначные сопоставления.
- `ExchangeLogger` — пишет только технические поля: время, режим, результат, число заказов и их числовые ID.

## Endpoint и протокол

Публичный адрес: `/theobroma-1c/exchange`.

Используется стандартный сценарий обмена CommerceML через запросы 1С:

1. `type=sale&mode=checkauth` — проверка Basic Auth.
2. `type=sale&mode=init` — объявление параметров обмена.
3. `type=sale&mode=query` — возврат одного XML-пакета с ожидающими заказами.
4. `type=sale&mode=success` — подтверждение успешно обработанного пакета.

`checkauth` возвращает протокольные строки `success`, имя cookie и непрозрачное значение сессии. `init` возвращает `zip=no` и ограничение размера. `query` возвращает UTF-8 CommerceML 2.05. `success` снимает отметку ожидания только с заказов последнего выданного пакета данной сессии.

Неизвестные `type` или `mode` завершаются HTTP 400. Ошибка аутентификации — HTTP 401 с `WWW-Authenticate`. Выключенный обмен — HTTP 503. Endpoint не принимает файлы и не выполняет импорт.

## Отбор и жизненный цикл заказов

Новый заказ становится ожидающим выгрузки только после подтверждённой оплаты. Источник истины — `WC_Order::is_paid()` и наличие `date_paid`, а не просто название статуса.

После первой выгрузки заказ снова становится ожидающим, если изменились:

- статус;
- состав или суммы;
- адрес или способ доставки;
- способ оплаты;
- отмена;
- полный или частичный возврат.

Неоплаченный заказ никогда не выгружается впервые. Если ранее выгруженный оплаченный заказ позднее отменён или возвращён, изменение выгружается независимо от текущего `is_paid()`.

В метаданных заказа хранятся:

- флаг ожидания;
- ревизия экспортируемых данных;
- подтверждённая ревизия;
- время последней успешной выгрузки.

Повторный `query` до `success` возвращает тот же логический пакет. Повторный `success` безопасен. Это обеспечивает доставку «как минимум один раз» без потери изменений; уникальный ID документа позволяет 1С обновлять заказ, а не создавать дубль.

## Формат заказа

Документ CommerceML использует стабильный ID `WC-ORDER-{order_id}` и номер WooCommerce. Передаются:

- дата создания и изменения;
- валюта и итог;
- покупатель и контактные данные;
- позиции, количество, цена до скидки, сумма и скидка;
- доставка отдельной услугой;
- сборы отдельными услугами;
- способ оплаты;
- признак оплаты и дата оплаты;
- статус WooCommerce;
- признаки отмены и финального состояния;
- возвраты с ID, датой и суммой;
- применённые купоны и сумма скидки;
- использованные и начисленные бонусы отдельными реквизитами.

XML формируется потоково через `XMLWriter`; весь пользовательский текст экранируется библиотекой. Денежные значения нормализуются до двух знаков без float-арифметики в межслойных контрактах.

## Идентификаторы товара

Стандартный WooCommerce SKU остаётся внутренним стабильным ключом каталога (`theobroma-*`) и не перезаписывается импортом Ozon.

Плагин добавляет метаполя:

- `_theobroma_1c_guid` — GUID номенклатуры 1С;
- `_theobroma_1c_article` — подтверждённый артикул 1С;
- `_theobroma_client_article` — артикул клиента/Ozon;
- `_theobroma_ozon_product_id` — Ozon Product ID;
- используется существующее `_theobroma_ozon_sku`;
- `_theobroma_ean` — штрихкод/EAN.

Основной `<Ид>` позиции выбирается в порядке:

1. GUID 1С;
2. подтверждённый артикул 1С;
3. артикул клиента;
4. внутренний WooCommerce SKU.

Тип выбранного ключа всегда передаётся отдельным реквизитом. Все непустые идентификаторы также передаются отдельными реквизитами. Если отсутствуют все четыре кандидата, заказ не подтверждается как выгруженный, а диагностика сообщает ID товара.

## Импорт таблицы Ozon

Администратор загружает `.tsv` или `.csv` не более 5 МБ. Поддерживаются русские заголовки из предоставленной выгрузки: `Артикул`, `Ozon Product ID`, `SKU`, `Штрихкод (Серийный номер / EAN)`, `Название товара`.

Импорт работает в два шага:

1. Предварительный просмотр ничего не записывает и показывает `matched`, `ambiguous`, `missing`, `invalid`.
2. Применение использует подписанный одноразовый token/nonce и записывает только строки `matched`.

Сопоставление с WooCommerce выполняется детерминированно:

1. ранее сохранённый Ozon SKU;
2. ранее сохранённый Ozon Product ID;
3. точное совпадение EAN;
4. явно заданная администратором пара.

Автоматическое сопоставление по названию запрещено. Название используется только как подсказка в отчёте. Неоднозначные строки требуют ручного выбора товара. Импорт записывает артикул клиента, Ozon Product ID, Ozon SKU и EAN, но не заполняет подтверждённый артикул 1С.

## Настройки и интерфейс

Страница `WooCommerce → Настройки → Интеграция с 1С` содержит:

- URL endpoint только для чтения;
- включение обмена;
- логин;
- установку/ротацию пароля;
- размер пакета заказов с безопасным пределом;
- диагностику требований;
- журнал последних обменов;
- импорт таблицы Ozon и отчёт сопоставления.

В редакторе товара появляется секция «Внешние идентификаторы». Поля валидируются по типу; Ozon ID/SKU — цифры, EAN — 8–14 цифр, остальные строки нормализуются и ограничиваются по длине.

## Безопасность

- Endpoint работает только по HTTPS вне локального окружения.
- Секрет хранится через `wp_hash_password`; сравнение выполняется `wp_check_password`.
- Настройки доступны только пользователям с `manage_woocommerce`.
- Все административные изменения защищены capability check и nonce.
- XML и журналы не сохраняются целиком.
- Логирование исключает имя, телефон, email, адрес, Basic Auth и session token.
- Ограничивается частота неуспешных попыток авторизации по хешированному IP-бакету.
- Импорт ограничен размером, типом файла и числом строк; формулы CSV не исполняются и не экспортируются обратно.

## Ошибки и наблюдаемость

Ошибка одного заказа не должна блокировать формирование остальных документов, но пакет не получает `success` для проблемной ревизии. В XML и журнал не попадают stack trace или секреты. Администратор видит код причины и ID заказа/товара.

Диагностика показывает:

- включён ли HTTPS;
- заполнены ли логин и пароль;
- доступен ли `XMLWriter`;
- число ожидающих заказов;
- товары без пригодного идентификатора;
- время и результат последнего `checkauth`, `query` и `success`.

## Совместимость и развёртывание

- Поддерживаются текущие версии PHP, WordPress и WooCommerce проекта, включая HPOS через публичные WooCommerce API.
- Плагин объявляет совместимость с HPOS.
- Сторонний EDI удаляется из обязательного установочного скрипта и проверки активных плагинов.
- Деактивация не удаляет настройки и метаданные.
- Удаление данных возможно только отдельным явно подтверждённым инструментом и не входит в первую версию.

## Тестирование

Чистые unit-тесты покрывают:

- приоритет идентификаторов;
- XML и экранирование;
- денежные значения, скидки, доставку и возвраты;
- правила первичной и повторной выгрузки;
- идемпотентность ревизий;
- разбор Ozon TSV/CSV и категории результата;
- запрет автоматического сопоставления по названию.

WordPress integration/smoke-тесты покрывают:

- регистрацию endpoint и HPOS-совместимости;
- Basic Auth и коды ошибок;
- настройки и права доступа;
- товарные метаполя;
- последовательность `checkauth → init → query → success`;
- отсутствие EDI среди обязательных плагинов.

Приёмочный тест использует оплаченный тестовый заказ со скидкой, доставкой и возвратом и проверяет XML по согласованному fixture без обращения к реальной 1С.

## Критерии готовности

- Неоплаченный новый заказ отсутствует в `query`.
- Оплаченный заказ появляется один раз на ревизию и исчезает после `success`.
- Отмена или возврат ранее выгруженного заказа создаёт новую ревизию.
- Каждая позиция содержит основной и все доступные внешние идентификаторы.
- Предоставленная таблица Ozon проходит preview без изменения каталога.
- Неоднозначные строки не применяются автоматически.
- В журнале нет секретов и персональных данных.
- Все тесты и smoke-проверки проходят.
